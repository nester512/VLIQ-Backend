# QR-приём чеков: сухие данные вместо файлов + проверка в ОФД с историей

Статус: **в работе** (решение владельца продукта 2026-10-08). Заменяет решения BRD «QR опционален,
отправка только из QR запрещена» и «сервер извлекает QR из файлов». Модерация, статусы, бонус,
выплаты — **без изменений**: меняется только вход.

## Решения (владелец продукта, 2026-10-08)
| Вопрос | Решение |
|---|---|
| Вход | Вариант **B поэтапно**: Ф1 — сканер Telegram + камера в приложении + ручной ввод; Ф2 — расшифровка QR из фото/PDF **в браузере**. На бэкенд — только данные. |
| Ответственность | Сканирование/ввод — на продавце; фронт валидирует и не отправляет мусор; продавец подтверждает данные. |
| Дубли (ФН+ФД+ФП) | **Только предупреждение** (как в BRD В-3-A): чек создаётся, продавец видит `POSSIBLE_DUPLICATE`, админ видит сигнал. |
| Проверка в ОФД | **Да.** Сразу после приёма; если не удалось — **cron** повторяет разными способами. Каждая попытка фиксируется, готовый ответ хранится, вся история видна по чеку. Ручная модерация остаётся. |

## Поток
```
Продавец ─ ① сканер Telegram  ② камера  ③ (Ф2) фото/PDF  ④ ручной ввод
   │
   ▼  фронт: разбор строки → {t,s,fn,i,fp,n} → строгая валидация → карточка подтверждения
   │         (n=1 приход; дата ≤ сейчас и ≥ сейчас−30 дн.; s>0; ФН 16 цифр; ФД/ФП цифры)
   ▼
POST /receipts/qr  {fn,fd,fp,t,s,n, qr_raw?, source, idempotency_key, brand_id}
   │  бэк: та же валидация (клиенту не доверяем) → 422; лимит частоты → 429;
   │       идемпотентность; дубль → предупреждение; Receipt(status=pending, source=…)
   ▼
воркер: фрод-проверки → попытка проверки в ОФД №1 → status=on_review (всегда; решение — админ)
   │        ok         → verification=verified: магазин, товары, сумма, предложенный бонус
   │        not_found / ошибка / лимит → verification=retrying, next_verification_at = backoff
   ▼
cron (каждые 5 мин): retrying & next_verification_at ≤ now & чек ещё on_review
   → следующая попытка другим способом → … → после N попыток verification=failed (ручная проверка)
```

## Модель данных (миграция `0009_qr_intake`)
`receipt`:
- `source` — `telegram_scan | camera_scan | image_decode | pdf_decode | manual | upload` (NULL у старых);
- `verification_status` — `not_required | pending | verified | retrying | failed` (старые/без QR — `not_required`);
- `verification_attempts`, `next_verification_at`, `verified_at`, `ofd_response jsonb` (готовый ответ).

`receipt_verification_attempt` (история, только вставка):
`id, receipt_id → receipt, attempt_no, provider, method, trigger (pipeline|cron|admin), outcome
(ok|not_found|mismatch|rate_limited|error|blocked), http_status, request jsonb (без токена),
response jsonb, error text, duration_ms, created_at`.

## Способы проверки (ротация по попыткам)
1. `fields` — fn/fd/fp/t/s/n, `t` без секунд, `s` в рублях `123.45`;
2. `qrraw` — строка QR как отсканирована (канонизированная, если вводили вручную);
3. `fields_seconds` — `t` с секундами (если были в QR), иначе `fields` повторно;
Следующий провайдер (ofd.ru / ФНС) подключается добавлением метода — без изменений схемы.

Расписание повторов: 5 мин, 15 мин, 1 ч, 3 ч, 6 ч, 12 ч, 24 ч, 48 ч → `failed`.
Повторы прекращаются, как только админ принял решение (approved/rejected/paid_out) — ручная проверка
приоритетнее. Админ может запустить проверку вручную (`POST /receipts/{id}/verify`, trigger=admin).

## API
- `POST /receipts/qr` (seller) — JSON, 202 `{receipt_id, warnings[]}`; 422 `QR_INVALID` с полем ошибки.
- `GET /receipts/{id}/verification` (admin) — статус + все попытки.
- `POST /receipts/{id}/verify` (admin) — внеочередная попытка.
- `POST /receipts/upload` — остаётся для совместимости (старые клиенты), фронт его больше не вызывает.

## Фронт
- `features/seller/qr/fiscalQr.ts` — разбор и валидация (зеркало `receipt_ocr/qr_parser.py`, общие фикстуры).
- Экран «Добавить чек»: «Сканировать QR» (Telegram `showScanQrPopup`; невалидный QR не закрывает
  сканер — показываем причину и ждём следующий), «Камера» (BarcodeDetector / zxing-wasm, вне Telegram
  и как запасной путь), «Ввести вручную» (дата/время, сумма, ФН, ФД, ФП). Далее — карточка
  подтверждения + «Данные с моего чека, отвечаю за их верность» → отправка.
- Локальная защита от повторной отправки того же чека с этого устройства (ФН:ФД:ФП).
- Админ: карточка без фото — данные QR, статус проверки ОФД, история попыток, «Перепроверить».
