# Переезд прода на новую версию: защита базы, ночная репетиция, выкатка

Прод: `shamilara.fun`, сервер `/srv/VLIQ-things/VLIQ-Backend`, ветка `main`. Переезжает всё, что есть в
`develop`: новые экраны, выплаты с чеками, путь чека, восстановление доступа и миграции базы
**0009–0014**. Правило владельца: **ни одна строка не теряется и не искажается**.

## Что делают миграции с данными
| № | Что | Существующие данные |
|---|---|---|
| 0009 | приём чеков по QR: новые колонки и таблица попыток проверки | не меняются; старым чекам — «проверка не нужна» |
| 0010 | индексы для быстрых списков (без блокировки таблиц) | не меняются |
| 0011 | «Путь чека» и список источников проверки | не меняются; старым чекам путь восстанавливается из истории |
| 0012 | выплаты: даты заявки, связь «заявка ↔ чеки» | не меняются; старым заявкам — даты и связь с чеками (с самых старых) |
| 0013 | восстановление доступа: таблица входов | не меняются |
| 0014 | «Выплачен» старым чекам | **меняется статус** одобренных чеков, полностью покрытых выплаченными заявками: «Одобрен» → «Выплачен» (решение владельца). Деньги не трогаются |

Все миграции только добавляют — старая версия кода работает с новой базой. Поэтому откат образа
не требует отката базы.

## 1. Защита базы — подготовить на проде ДО выкатки
| # | Что | Кто | Как проверить |
|---|---|---|---|
| 1 | Тома с данными объявлены внешними (база, файлы чеков, TLS). `docker compose down -v` их не удалит; без тома прод не стартует на пустой базе | в коде (`docker-compose.test.yml`) | на сервере: `docker volume ls \| grep vliq-backend_` → есть `postgres_data`, `minio_data`, `caddy_data`. Если имён нет или они другие — **не выкатывать**, поправить имена в оверлее |
| 2 | Ночной бэкап базы, независимо от выкаток | ответственный за сервер | cron из `ops/backup/nightly.sh`; в `.deploy/backups/nightly.log` каждое утро строка `OK` |
| 3 | **Копия бэкапа вне сервера** — бэкап на том же диске погибает вместе с диском | владелец решает, где хранить (объектное хранилище, другой сервер); сервер — настраивает `BACKUP_UPLOAD_CMD` | в логе `uploaded off-host`, а не `WARNING` |
| 4 | Бэкап перед каждой миграцией и проверка места на диске | в коде (`ops/deploy.sh`) | без бэкапа или при нехватке места миграция не запускается |
| 5 | Выкатка на прод только после ручного подтверждения | владелец: GitHub → Settings → Environments → `test` → Required reviewers | после слияния в `main` деплой ждёт кнопку «Approve» |
| 6 | Запрещённые на проде команды: `docker compose down -v`, `docker volume rm`/`prune`, `docker system prune --volumes`, ручной SQL без бэкапа и «да» владельца | все, у кого есть доступ | `CLAUDE.md`, этот документ |
| 7 | Доступ к серверу и Docker — минимальному числу людей | владелец | список ключей SSH |

## 2. Ночь 1 — репетиция на копии данных прода
Запускается **на прод-сервере** ночью. С живой базы только снимается дамп (чтение). Миграции идут на
временной копии в отдельном контейнере без доступа в интернет; копия удаляется сразу после проверки.
Отчёт содержит только количества, суммы и контрольные хэши — без персональных данных.

```bash
cd /srv/VLIQ-things/VLIQ-Backend
git fetch origin && git checkout --detach <SHA релиза из develop>
IMAGE_TAG=<тот же SHA> ops/migration/rehearse.sh
```

| Проверка | Что значит PASS |
|---|---|
| Старые данные не изменились | 13 таблиц — каждое значение каждой строки до и после совпадает (контрольная сумма); деньги по видам операций и заявки по статусам — те же суммы |
| «Выплачен» от 0014 | «Одобрен» уменьшился ровно на столько чеков, сколько отметила миграция, «Выплачен» — увеличился на столько же |
| Ни один чек не потерялся | общее число чеков до и после одинаково |
| 14 проверок после миграции | у каждого чека есть путь; заявки не покрывают больше своей суммы; чек не покрыт больше своего бонуса; нет недостроенных индексов; никому не закрыт вход и т. д. |
| Откат возвращает всё как было | после отката к прежней схеме отпечаток данных совпадает с исходным |
| Повторный запуск ничего не меняет | второй прогон миграций даёт тот же результат |

Итог: `REHEARSAL PASS` или `REHEARSAL FAIL` с перечнем расхождений. Отчёт — в
`.deploy/rehearsal/<время>-<sha>/`. В нём же время миграции: от него зависит окно выкатки. На копии
данных стенда (75 тыс. чеков) миграции заняли 6 секунд.
`INFO` в отчёте — сведения для владельца, например продавцы с отрицательным балансом. На итог они не
влияют: миграции деньги не трогают, это доказывает первая проверка.

**FAIL — не выкатываем.** Отчёт (только агрегаты) передаётся разработчику, исправление идёт через
стенд, затем новая репетиция.

## 3. Ночь 2 — выкатка
До начала:
- [ ] CI на `develop` зелёный, регресс стенда пройден (`docs/testing/REGRESSION.md`: API `fail=0`,
      экраны `LAYOUT issues=0`, `BACK fails=0`);
- [ ] репетиция `PASS` на дампе не старше суток, тот же SHA;
- [ ] пункты 1–5 раздела «Защита базы» выполнены; свежий ночной бэкап лежит **вне сервера**;
- [ ] владелец дал «да» на выкатку.

Шаги:
1. Слить `develop` в `main` (fast-forward, тот же SHA, что проверен на репетиции).
2. CI собирает образы, деплой ждёт подтверждения → владелец нажимает «Approve».
3. `ops/deploy.sh` сам: проверка места → бэкап с проверкой → миграции → переключение контейнеров →
   проверка `/health`. Если миграция упала — контейнеры не переключаются. Если не поднялось
   приложение — автоматический откат образа.
4. Сразу после — проверки на живой базе (только чтение):
   ```bash
   C="docker compose -f docker-compose.yml -f docker-compose.test.yml"
   $C exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -At -F "|"' < ops/migration/invariants.sql
   ```
   Каждая строка, кроме `info_…`, должна заканчиваться на `|0`. Числа в `money.*` и `receipt.status.*`
   из `fingerprint.sql` сравнить с отчётом репетиции: разница — только действия, сделанные между
   дампом и выкаткой.
5. Ручная проверка (на проде **не** запускаем API-регресс: он создаёт данные):
   - вход админа, сводка — числа похожи на прежние;
   - колода проверки, «Все чеки», «Выплаты» с итогами, страница продавца, «Путь чека» у старого чека;
   - вход продавца, баланс и история совпадают с прежними; у выплаченных старых чеков статус «Выплачен».
6. Первые часы: логи бэкенда, недоставленные уведомления (`notification_outbox_dead`), жалобы продавцов.

## 4. Если что-то пошло не так
- **Ошибка в приложении** — откат на прежнюю версию программы, база остаётся как есть (миграции
  совместимы со старым кодом). Из текущей папки, не переключая git на старый коммит:
  `IMAGE_TAG=$(git rev-parse <прежний SHA>) DEPLOY_SKIP_MIGRATIONS=1 ./ops/deploy.sh`.
- **Испорчены данные** — только с «да» владельца. Сначала дамп текущего состояния, потом
  восстановление из бэкапа перед миграцией (`docs/CI-CD.md`, «Восстановление из бэкапа»). Всё, что
  продавцы и админы сделали после бэкапа, будет потеряно, поэтому сначала оцениваем точечное
  исправление.

## Скрипты
| Файл | Что делает |
|---|---|
| `ops/migration/rehearse.sh` | репетиция на копии: дамп → копия → миграции → сверка → откат → повтор → удаление копии |
| `ops/migration/fingerprint.sql` | отпечаток данных до / после (агрегаты) |
| `ops/migration/invariants.sql` | проверки после миграции |
| `ops/migration/compare.sh` | итог репетиции PASS / FAIL |
| `ops/backup/nightly.sh` | ночной бэкап с проверкой и копией вне сервера |

Проверено на стенде 2026-10-13: копия базы стенда, откат к схеме прода (0008) → полный путь до 0014 →
`REHEARSAL PASS`. Сверка ловит порчу: искажённая сумма или чек без пути дают `FAIL` с точной строкой.
