## Что это
VLIQ — мотивационная программа для продавцов бренда. Продавец отправляет кассовые чеки с продажами
продукции. Администратор проверяет каждый чек вручную и назначает бонус. Накопленный бонус продавец
выводит заявкой на выплату через СБП. Всё работает внутри Telegram: Mini App и бот.

## Роли
| Роль | Кто | Как получает роль |
|---|---|---|
| Продавец | участник программы | автоматически при первом входе в Mini App |
| Администратор | представитель бренда: проверка чеков, выплаты, продавцы | запись в БД (экрана управления админами нет) |
| Super admin | то же, что администратор, плюс 2 действия без экрана: восстановление доступа продавца и настройка источников проверки | запись в БД |

Бренд в системе один. Привязка продавца к бренду по ссылке не сделана (out of scope).

## Статусы чека
| Статус | Продавец видит | Смысл |
|---|---|---|
| Принят, обрабатывается | «На проверке» | первые секунды после отправки |
| На проверке | «На проверке» | ждёт решения админа |
| Одобрен | «Одобрен» | админ назначил бонус, бонус на балансе |
| Отклонён | «Отклонён» + причина | конечный |
| Выплачен | «Выплачен» | бонус по чеку полностью покрыт оплаченной выплатой |

Статуса «на доработке» в продукте нет: плохой чек отклоняется, продавец может отправить его снова.

Автоматическая проверка чека (ФНС/ОФД) — отдельная отметка «подтверждён / не подтверждён».
Она **не меняет статус и бонус**, решение всегда за админом.

## Деньги — общие правила
- Бонус за чек назначает админ вручную. Автоматического расчёта бонуса нет.
- История денег продавца только пополняется. Любое изменение суммы — новая запись с причиной.
  Старые записи не правятся и не удаляются.
- Минимальная сумма выплаты — **3 000 ₽** (настройка сервера). Ограничений на частоту заявок нет.
- Выплата — только СБП по номеру мобильного телефона РФ. Номер вводится в каждой заявке и в
  профиле не хранится.
- Деньги заявки резервируются сразу при создании, поэтому одни и те же деньги нельзя вывести дважды.
- Админ платит **вручную, вне системы**, затем отмечает заявку выплаченной.
- Отменить одобренный или выплаченный чек, уменьшить его бонус или удалить его можно только с
  причиной. Если чек уже выплачен, у продавца появляется долг (отрицательный баланс). Долг гасится
  следующими начислениями.

## Блокировка продавца
Заблокированный продавец не может войти в приложение, отправлять чеки и запрашивать выплаты.
Его чеки уходят из очереди проверки, заявки — из очереди выплат. Данные не удаляются, после
разблокировки всё возвращается.

## Минимальные требования
**Продавцу и админу:**
- Telegram на смартфоне. Вне Telegram приложение не открывается (показывает «Приложение доступно
  только через Telegram»).
- Встроенный сканер QR — мобильный Telegram с поддержкой Bot API 6.4 и выше.
- Если встроенного сканера нет — камера телефона с разрешением доступа. Без камеры остаются
  фото/скриншот/PDF чека или ручной ввод.
- Файл чека для распознавания QR: до 25 МБ, PDF до 50 страниц. Файл на сервер не отправляется.
- Ширина экрана от 344 px (проверено на Galaxy Z Flip 7).
- Интернет.

**Серверу:**
- Docker и Docker Compose.
- Сервисы: PostgreSQL 16, Redis 7, MinIO (файлы старых чеков), backend, бот, воркер уведомлений,
  воркер проверки чеков, frontend, Caddy (HTTPS).
- Мониторинг (Prometheus, Loki, Grafana) — по желанию.
- Публичный домен с HTTPS, токен Telegram-бота.
- Для автоматической проверки чеков — платная подписка proverkacheka.com (токен).
- Нагрузка: на стенде весь стек без мониторинга занимает около 0,8 ГБ памяти. Замер 2026-10-09, на
  синтетических данных. Сервер стенда — 4 vCPU, 8 ГБ, и он общий с другими проектами. Нагрузочного
  теста под прод-объём не было.

## Out of scope (решено не делать сейчас)
- Автоматический расчёт бонуса (по товарам, по акциям, «фикс за чек»).
- Подсказка админу ставки по условиям акции.
- Акции: создание админом и витрина у продавца. Экран-заглушка «будет доступен позже».
- Раздел «Товары» у админа. Экран-заглушка.
- Статус «на доработке» и сценарий переотправки чека.
- Уведомления админам: о новых чеках, о заявках на выплату, о действиях продавцов.
- Центр уведомлений внутри приложения. Уведомления — только сообщениями бота.
- Привязка продавца к бренду по ссылке или коду. Бренд один.
- Экран управления администраторами. Админы добавляются записью в БД.
- Экраны для действий super admin (восстановление доступа, источники проверки). Сейчас только API.
- Редактирование профиля продавцом после регистрации. Изменения — через поддержку.
- Отмена заявки на выплату продавцом.
- Выгрузка выплат в Excel. Кнопка показывает «скоро».
- Лимиты частоты заявок на выплату (есть только минимальная сумма).
- Самостоятельное восстановление доступа по номеру телефона.
- Разделение одной отправки с несколькими чеками на несколько чеков.

## Принятые решения
Действуют на 2026-10-09. Прежние решения, которые этими отменены, здесь не повторяются.

| № | Тема | Решение |
|---|---|---|
| В-1 | Блокировка | Двойной заслон: не пускать в приложение **и** запрещать действия, даже с открытой сессией |
| В-3, В-17 | Дубли | Совпадение ФН+ФД+ФП с другим чеком — **только предупреждение**. Решает админ, он видит исходный чек. Сверка — только среди чеков QR-приёма |
| В-4 | Главный экран / баланс | Количество чеков на главном экране, суммы на экране баланса |
| В-5 | Реквизиты | Вводятся в каждой заявке; только СБП по телефону |
| В-6 | Акции | Акция информационная, админ учитывает её сам, назначая бонус |
| В-8 | «Выплачен» | Статус ставится на каждый чек, покрытый оплаченной выплатой. Покрытие — с самых старых одобренных чеков, частичное возможно |
| В-10 | Super admin | Не продуктовая роль: доступ к БД плюс два действия через API |
| В-11 | Минимум выплаты | 3 000 ₽ |
| В-12 | Чеки в выплате | Заявка всегда связана с чеками, которые она покрывает |
| В-13 | Дубли заявок | Одна отправка формы — одна заявка; строгая проверка номера СБП |
| В-14 | Деньги назад | Только отдельной записью с причиной; у выплаченного чека — долг продавца |
| В-15 | Отказ по заявке | Только с причиной, продавец видит её; статус «в обработке» и журнал действий есть |
| В-16 | «На проверке» в балансе | Сумма бонусов нерешённых чеков, плюс их количество |
| QR (2026-10-08) | Приём чеков | Только данные QR, без файлов: скан, фото/PDF с распознаванием на телефоне, ручной ввод. За данные отвечает продавец |
| Путь чека (2026-10-09) | Проверка | Каждая проверка у источника и каждое действие хранятся в «Пути чека». Источники по порядку: ФНС → proverkacheka → ОФД. Продавец видит только статус |
| В-18 | Потеря Telegram | Ручное восстановление через поддержку и super admin ([05-operations.md](05-operations.md)) |
| 0014 (2026-10-09) | Старые выплаты | Старым чекам, полностью покрытым оплаченными выплатами, «Выплачен» ставится миграцией при выкатке |
